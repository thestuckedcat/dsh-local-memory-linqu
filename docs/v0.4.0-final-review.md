## 新增发现

### NEW-C1（Critical）纠正的重新入队被旧队列身份校验拒绝，纠正事实仍不会保存；单测用 stub 掩盖

- 实现：`plugin/correction.mjs:68-89` 在挂起后调用 `info.binding.queue.enqueue({requestId:'correction-v1:…', sourceRef, sourceVersion, purpose:'memory_extract', generation: store.generation()})`。
- 但 `plugin/session-hooks.mjs:86-88` 已在同一 admission 事务内先入队了**同 sourceRef/sourceVersion/purpose** 的原始 `memory_extract` job；旧队列按 `event_key=fingerprint({source,purpose,itemRef})` 去重（`src/jobs.mjs:70-74`），再次入队会命中原始 job 而 payload 不同（generation 不同）→ 抛 `Request/source identity changed`，被 correction 的 catch 计入 `failed`，事实不保存。
- 独立复现（临时 store + 真实 `createJobQueue`）：先入队原始 extract job，再 `suspendForCorrection` 推进 epoch，再以新 generation 入队同 source/purpose → **`{"error":"Request/source identity changed"}`**。
- 测试为何没发现：`tests/correction.test.mjs:39-42` 使用 `{enqueue: (args)=>enqueued.push(args)}` 的 stub queue，不经过 jobs.mjs 的身份校验；`tests/plugin-entry.test.mjs` 没有 correction 集成用例。
- 连带问题：`plugin/index.mjs:200-222` 的 `enqueueAnnualDraft` 使用 `info.binding.generation`（挂起前的旧 epoch）→ `checkEpoch` 失败并被吞（`annual_draft_refused`），响应第 38 行“年度草稿使用新 epoch”不成立。
- 影响：用户明确纠正后，旧记忆被挂起，但新事实不会进入记忆；比 addendum 前“整条消息直存（至少保存了文本）”更差。属于本轮新引入/未验证的回归，不能算 I-4/N-1 已关闭。

### NEW-I1（Important）worker recovery 只恢复 queued，running/ready 作业永久卡住

- `plugin/consolidation-operations.mjs:190-215` 的 `recover()` 只扫描 `queue.list({state:'queued'})` 且要求存在 publication 行；**从不调用** `queue.recoverInterrupted()`。
- 独立复现：把 queued job 手动置 `running` 后重启 ops 实例，`recover()` 返回 0、`tick()` 为 skipped、job 仍为 `running`；运行中进程崩溃后也无人将其转 `outcome_unknown`。`ready`（模型已完成、尚未 publish）同样不在恢复范围，候选会被遗弃。
- 与 `docs/mechanisms.md:286` `MEM-CONSOL-QUEUE-01` "running 恢复置 unknown" 及设计 §7.2/§7.4 冲突；README `:154` 仅说 recover queued（准确但不完整，容易读成完整恢复）。

### NEW-I2（Important）`consolidation.enabled=false` 不能阻止已持久化的自动 job 在重启后执行

- `plugin/consolidation-operations.mjs:84` 只在 `autoEnqueue()` 检查 `config.consolidation.enabled`；`recover()`（`:190-215`）和 `tick()` 处理已入队 pending job 时**不检查该开关**。
- 独立复现：auto 配置下用 fake dirty 入队自动 job（`request_id` 以 `auto-consolidate:` 开头并带 publication 行），重启时使用 `consolidation.enabled:false` 的新 worker：`recover()` 返回 1，`tick()` 直接 publish，head 变成新版本。
- 影响：用户关闭自动整理后，之前排队/持久化的自动 job 仍会在下次启动执行；与“用户关闭 consolidation 停止新工作”、默认关闭的语义不一致；也说明 publication 行被当作可跨重启、跨配置变更的通行证。

### NEW-I3（Important）worker 模型调用缺少真实的执行授权/预算/派发前空闲仲裁

- `plugin/consolidation-operations.mjs:102,129,201` 为 manual/auto/recover 三种路径注入的 `authorizeExecution` 都是**自签名字符串**（`local-user-consolidation:<jobId>` 等），不检查 host-grants 的会话/receipt/lease/`authorizationVersion`；`plugin/index.mjs` 也没有把 `grants` 传入该模块。`MEM-CONSOL-RUN-01` 所称“同步可信 execution 授权”在最新 worker 路径中不成立。
- 模块不消费 `config.limits`，没有 design §4.3 的整理 dailyRequests/cooldown 子预算，也没有 profile dispatch broker；auto 触发每批 2..maxMemories 条（config 允许 16，默认 8，而 BG-S04 设计为最多 5 条）即可发模型请求。证据 limitations 仅说“profile budget broker 未实现”，但新 auto 路径已经实际可通过 config 启用发请求，属于未受预算门约束的新出口。
- 前台仲裁：`tick()` 只在 `runJob` 前调用 `canDispatch()`（`:147/:154`），进入 `prepareCall` 的 await 后不再复核 idle（`plugin/harness-provider.mjs:88` 之后无 idle gate 检查）；`busyGate` 也只看 agent status，不是 BG-S03 要求的“所有会话/子任务无生成/工具执行/排队请求”。真实 Host idle 事件尚未验证。
- 结论：这是增量功能的安全/成本边界缺口，不要求本轮实现完整 budget broker，但文档不能把它表述为已有可信执行授权。

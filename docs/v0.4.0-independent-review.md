## Critical

### CR-1 明确删除/纠正后，被删正文仍保留在整理输入（`consolidation_inputs`），违反"删除即清除"

**证据**
- `src/lifecycle.mjs:15-27`：`forget` 只清 `records`、撤销条目、清 `job_inputs`（旧队列）并调用 `purgeExcerptsForMemory`/`purgeDerivedForMemory`；没有清 `consolidation_inputs` 或 `consolidation_jobs`。
- `src/store-internals.mjs:47-53`：`advance(ctx,{lifecycle:true})` 只把旧 epoch 的**旧** `ledger.jobs` 置 stale 并删 `job_inputs`；对 v0.4 新增的 `consolidation_jobs` / `consolidation_inputs` 没有任何处理。
- `src/store-internals.mjs:235-252`：`purgeDerivedForMemory` 只删 candidate/version body、tombstone entry、清 head，不触碰整理输入和整理作业行。
- `src/consolidation-queue.mjs:110-111`：整理输入是完整 `InputSnapshot`（含每条记忆 `text`）的 `payload`。
- 与设计不符：`docs/memory-consolidation-design.md:391`（§8.2）明确要求 `advance(...lifecycle:true)` "同时把所有旧epoch的整理input/candidate标失效并实质清正文"，且 `invalidateConsolidation` 必须从 `forget/archive/correctMemory/consumeCapabilityEvent` 原事务内调用。

**最小复现（临时 store，未写仓库）**：创建 2 条记忆 → `enqueue` 一个整理任务 → `store.forget` 其中一条后查询：`consolidation_inputs.payload` 仍存在，且仍包含被删记忆的完整文本片段（canary 命中），`consolidation_jobs.state` 仍为 `queued`。另测：入队后仅新增一条无关记忆，`runJob` 因 `MC_REVISION_CHANGED` 抛错，作业仍停留在 `queued` 且输入保留（见 I-7）。

**影响**：本项目把"记忆中心删除即清除、归档才可恢复"作为用户已确认的硬语义（`TODO.md:13`、`README.md:82`、`docs/mechanisms.md` MEM-CONSOL-LIFE-01）。该缺陷使删除后的正文在工具控制的 content DB 里仍有第二份完整副本，且作业继续占用每 scope 2 个排队容量；设计要求的"删除传播"只完成了 candidate/version 一半。由于当前没有到达该队列的产品入口（I-1），现网用户触发路径有限，但一旦接线，这就是删除保证的直接破坏；修复方向应是删除/纠正事务内清 `consolidation_inputs` 并把相关 `consolidation_jobs` 置 stale（本评审只报告，不修码）。

### I-4 纠正挂起会连带作废同一条消息触发的新提炼/年度草稿任务（纠正的事实不会被保存）

- 顺序：`plugin/session-hooks.mjs:84-92` 在**同一个 `write` 事务**里先 `binding.queue.enqueue(...)`（`memory_extract`，`generation=frame.binding.generation`），随后调用 `onMessageAdmitted`；`plugin/index.mjs:371-374` 在该回调里先 `enqueueAnnualDraft`、再 `correction.onMessageAdmitted`；`plugin/correction.mjs:52-56` 对 cited 记录调用 `store.suspendForCorrection`；`src/store-internals.mjs:47-53` 的 `advance(ctx,{lifecycle:true})` 会把 **epoch<>新 epoch 的所有 queued `ledger.jobs` 置 stale** 并删除其 `job_inputs`。因此纠正消息刚入队的提取任务（及年度草稿任务）会被立即标 stale，纠正后的新事实不会走正常提炼路径。
- 这与 `plugin/correction.mjs:7-9` 的注释"the current user message still goes through the normal extraction/admission path"以及 `docs/memory-experience-contract.md:31`（"把用户的纠正连同当前消息来源保存"）不符；`tests/correction.test.mjs` 只有单元测试（synthetic attribution + store），没有 `plugin-entry` 集成用例覆盖这一顺序，故测试全绿仍漏掉该缺陷。
- **影响**：用户说"这里已经改了/上次理解错了"后，旧记录确实挂起，但新事实不会被记忆；当前版本又未实现后台反思（EXP-T4 未完成），因此纠正闭环实际断开。按设计应把纠正放在入队之前、或让纠正不造成本次消息任务的 generation 失效。

### I-6 整理链路的授权/CAS 与设计合同有实质缺口：发布不复核批次许可、无 publication 权限、enqueue 硬编码用户 actor

- `src/consolidation-versions.mjs:78-129` 的 `publish` 只核 candidate digest、epoch、scopeRevision、headRevision、job ready、依赖活性；**完全没有**复核 batch permission/过期/撤销，也没有创建/校验 publication permission。`getVersion`（`131-162`）只按 entry 状态与依赖活性读取，没有 publication 权限检查。
- 设计明确要求：`docs/memory-consolidation-design.md:344-349`（`authorizeExecution` 四阶段、`authorizePublication` 写无 TTL publication 权限、读时核 publication）、`:384`（publish 在事务内 `authorizePublication`）、`:395`（Version read 核 publication 与各 excerpt TTL）。实现中 `consolidation_permissions` 表只被 batch 使用，`kind='publication'` 从未写入。
- `src/consolidation-queue.mjs:105` 在 `enqueue` 内固定 `authorizeBatch({..., actor:'user'})`；`queue.enqueue` 本身**没有 actor 参数**，任何未来调用者（包括模型/管理 dispatcher 的错误分支）都会得到"用户已授权"的批次许可。设计 `:346` 规定只有同源/用户手势 handler 可调用 `authorizeBatch`。此外 `assertCurrent`（`src/consolidation-inputs.mjs:212-235`）没有重核 route/config digest/policy revision（`permissionCurrent` 只核 subject/expiry/state，`203-210`），与设计 `:147-148`、`:347` 的"policy/config/route 变化使 lease 失效"不一致。

### I-7 整理队列生命周期不健壮：预检失败后作业永久停在 `queued` 并保留输入；running 取消不 abort 且被标为 `cancelled`

- `src/consolidation-queue.mjs:199-210` 在 claim 事务内调用 `inputs.assertCurrent`；一旦失败（例如入队后普通 `store.put` 使 revision 改变，`src/consolidation-inputs.mjs:223`），异常从事务抛出，作业**保持 queued**、`consolidation_inputs` 保留，占满每 scope 2 个容量（`queue.mjs:98,106`）。没有代码把这种不可再通过预检的作业转 `stale`，`recoverInterrupted`（`:160-171`）只处理 `running`。临时复现：入队后新增一条无关记忆，`runJob` 抛 `MC_REVISION_CHANGED`，随后 job 仍 `queued`、input 仍存在、`pending()` 容量被占用。
- `src/consolidation-queue.mjs:144-159` 的 `cancel` 对 `running` 作业也直接置 `cancelled`；`runJob` 的 `AbortController`（`:219-233`）只服务超时，没有登记到 job，cancel 无法 abort 在途 Provider 调用；作业被标成终态 `cancelled`，而远端是否已执行未确认。设计 `docs/memory-consolidation-design.md:370-372` 要求 running cancel 先 abort lease，未确认远端终止则 `outcome_unknown`，不能冒称 cancelled。
- **影响**：当前无入口；接线后会造成队列饥饿/容量泄漏、删除文本滞留（CR-1）和成本状态误报。

### I-8 归档与 capability 事件路径没有派生失效传播，设计 §8.2 的单一入口 `invalidateConsolidation` 未落地

- `src/lifecycle.mjs:29` 的 `archive` 只 `advance` + 改 state，不清候选/版本文本、不处理 head；`forget`/`correctMemory` 才在 `:23`/`:42` 调 `purgeExcerptsForMemory`+`purgeDerivedForMemory`。`evidence/consolidation-propagation.json` limitations 已承认"归档传播未实现"，但 `docs/mechanisms.md:289` `MEM-CONSOL-LIFE-01` 只写"原记忆删除/纠正"，README `:82` 也只说删除 vs 归档；没有一处把"归档不传播派生"写进用户可见限制。
- `src/lifecycle.mjs:71-88` 的 `consumeCapabilityEvent` 只写 `source_blocks`、把 entries 置 `stale`；既不清 `consolidation_excerpts` 正文，也不清 candidate/version 正文、不推进/清空 `consolidation_head`。设计 `docs/memory-consolidation-design.md:391` 明确把 `consumeCapabilityEvent` 列为 `invalidateConsolidation` 的调用方。后果：归档后 `getVersion` 因依赖非 active 而 fail-closed（`src/consolidation-versions.mjs:26-34,143`），但 head 仍指向失效版本，`memory.derived` 从"head:null"变成报错；`getCandidate`（`:58-77`）不核依赖，库内仍可读候选正文。
- **影响**：删除/纠正之外的失效路径与设计不一致，部分正文保留时间超出"派生正文随源失效而清除"的声明。

### I-9 多仓项目下 `memory.derived`/`memory.excerpts` 固定取"第一个 enabled 仓库"，返回错误或空数据

- `plugin/experience-operations.mjs:46-48`（derived）和 `:85-89`（excerpts）都用 `(project.repositories ?? []).find(entry => entry.enabled)` 选一个 scope；但 M2 明确支持一个逻辑项目多个 repo/scope（`README.md:79`、`TODO.md:75` MEM-201），整理 head 与摘录都是 per-scope（`src/consolidation-versions.mjs:19-21` 按 `scope_ref` 读 head）。
- 因此：多仓项目中 `memory.derived` 只显示第一个仓库的已发布 head（其它 scope 的 head 永不展示），`memory.excerpts` 对第二个仓库里的 memoryId 会返回空列表。测试只用单仓库 fixture（`tests/consolidation-versions.test.mjs:126-133`、`tests/experience-operations.test.mjs:48-59`），未覆盖多仓。
- **影响**：这是当前**已接线、用户可调用**的只读 API（`memory.derived` 已在真实安装态返回 `head:null` 验证通过）的语义缺陷；M2 多仓项目会看到不完整/错误的派生视图与空摘录列表。

**不能称 v0.4.0 为完整 05 交付。** 它是一份"v0.3.0 + 体验/后台增量 + M3 骨架"的增量版本：

- 但按审查目标 1–3，本版本在**删除保证（CR-1）**、**整理授权/CAS（I-6）**、**纠正闭环（I-4）**、**整理队列生命周期（I-7）**、**失效传播（I-8）**、**空闲安全门（I-5）**和**多仓只读视图（I-9）**上存在真实缺陷；同时摘要文档把没有产品入口的整理后端写成已交付（I-1），机制/README 主体仍是 v0.3.0 文本并含错误否定（I-2），最终证据的完整性字段是恒真且 README 已漂移（I-3）。

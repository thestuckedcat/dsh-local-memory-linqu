## 结论与适用范围

两种方向有明确差异：A 用摘要、来源和相近双栏比例支持阅读；B 用状态列、选择栏和略宽列表支持比较。四分区与列表加侧边详情均保留，没有加入 KPI 看板、图谱或新的信息层级。就源码结构而言，比较对象成立；哪种更简洁、清晰仍须由用户实际观察后决定。

0.1 初审发现 4 项 Important、4 项 Minor；**0.2 的八项修正已关闭，当前未关闭 Important 0、Minor 0**。关闭依据为本评审者的独立源码复核，以及主协调者对同一原型字节执行的离线浏览器回归结果（19/19）。本评审者只核对回归脚本和结果，未执行该浏览器运行或独立查看截图；这不是用户视觉选择或真实宿主 UI 验收。此次是评审素材修正，不是继续实现记忆整理、批量写入或其他新业务能力的授权。

用户整体视觉选择仍是 **pending**：设计稿 UI-REV-02/03 标为未确认，第 3 节的用户答复/预测仍待完成；离线 A 的默认选中、切换方向、原型里“采用候选”均不等于用户确认 A/B。

## 0.1 初审 Important（历史发现）

### UI-REV-I01：B 的隐藏所选项可打开空详情，并使窄屏失去返回入口

- **位置**：原型 `render()` 的筛选和详情查找（230、240–243 行），`selected` 动作（256 行），筛选/搜索事件（261、265 行），空详情（220 行）与窄屏隐藏列表规则（138–141 行）。
- **反例**：在 B 勾选 DEMO-E01，再搜索只匹配 DEMO-E02 的“缓冲区”，随后按“查看首条所选”。`checked` 仍包含 E01，按钮保持可用；动作选中 E01，但详情只从当前 `items` 查找，于是渲染空详情。窄屏下 `detailOpen=true` 隐藏列表；空详情没有“返回列表”。这是静态控制流可确定的路径，浏览器实际表现尚待复核。
- **影响**：用户无法通过可见返回按钮完成主旅程；选择数量和当前结果也不一致。Escape 虽存在恢复分支，但界面没有告诉用户必须依赖它。
- **修正建议**：本原型可在筛选/搜索改变时，把勾选集合收敛到当前结果，或明确采用跨筛选选择并在打开前恢复相应结果；两者选其一，不必询问用户内部机制。打开前确认目标可呈现。空详情也必须保留返回路径。窄屏按“勾选→排除→查看”复核，完成标准是始终存在有效详情或解释与返回，且不留下隐藏焦点。

### UI-REV-I02：年度记录的“已审定”混淆记录确认与报告审定

- **位置**：合成记录 DEMO-A03（170 行）与年度通用详情（222–224 行）；设计稿第 4.3 节。实现对照：`client.js:1346` 的 `report.approve`，`client.js:1428`/`1438` 的断言/时间“已确认”。
- **反例**：一条工作记录的本人贡献已确认，但结果仍缺证明；该记录曾被纳入某次报告审定。若列表直接写绿色“已审定”，用户会把它理解成整条记录及其证明均已审定，且对后续版本也持续有效。
- **影响**：当前实现审定对象是报告，绑定 `reportDigest + sourceRevisions`；工作记录的确认、证明支持、证明是否已读分别存在。“合成”提示能说明数据真假，不能消除状态对象的歧义。
- **修正建议**：普通记录使用“已确认/待确认”或具体的“结果待补证明”等状态；若要展示报告审定，明确类型为报告，显示报告版本/来源绑定，或写“已纳入已审定报告（来源版本…）”。保留“未读证明≠已证实”和“普通经验仍未核验”的分界，不新增普通经验核验按钮。

### UI-REV-I03：整理对比未提供可闭合的两条原文与来源链

- **位置**：经验合成数据（162–165 行）、候选 DEMO-C01（173 行）、硬编码对比与来源（223–224 行）。
- **反例**：候选称来源为 DEMO-E03＋DEMO-E05，但经验集合中只有 E01–E04；E05 不存在。对比区第一条显示 E03 的标题式短句，没有展示 E03 的完整 `text`；来源区第一块是两个记录 ID 的总称，第二块才是某个对话引用，无法逐条核对两条原文分别来自何处。
- **影响**：原型声称“逐条原文/建议/来源对照”，用户实际只能评审压缩过的说明，无法判断候选是否遗漏了条件。这会直接影响用户对整理功能形态的判断。
- **修正建议**：把两条待整理的合成记录作为真实存在的合成对象，每条显示稳定 ID、完整原文、各自来源与定位；候选只引用这两个对象，避免另写一份不同的原文。仍保留“设计候选、未实现、仅本页决定”，不增加 API 或真实写入。完成标准是能从候选逐条找到两份原文及其独立来源，数量和文案一致。

### UI-REV-I04：两个程序打开详情的入口未恢复可见焦点

- **位置**：普通记录点击有窄屏 `back.focus()`（249 行），但 `organize`（251 行）和 `selected`（256 行）没有同等处理；通用焦点保留（227–228、243 行）只按原动作寻找替代节点。
- **反例**：窄屏用键盘按“整理记忆（设计预览）”，分区切到处理任务后原按钮被隐藏；或在 B 按“查看首条所选”，列表连同原按钮被隐藏。两条路径都没有把焦点送入可见详情。即使所选记录在当前结果内，此问题仍可单独发生。
- **影响**：详情已经改变，但键盘/辅助技术用户没有可见的起点；同一详情通过不同入口打开时行为不一致。
- **修正建议**：将“打开详情”的状态与焦点处理统一：窄屏打开后聚焦返回按钮或可聚焦标题，返回聚焦原记录；若原记录不存在，聚焦列表标题或筛选工具栏。每条入口均复核 Tab、Shift+Tab、Enter/Space、Escape。不要求叠层或新增焦点陷阱。

## 0.1 初审 Minor（历史发现）

### UI-REV-M01：移动搜索字号的声明与实际继承不同

- **位置**：`.mc-field` 为 12px（52 行），控件 `font:inherit`（42 行），移动仅将 `.mc-product` 改为 16px（129 行）；设计稿第 6 节宣称移动搜索 16px。
- **反例**：搜索输入位于 `.mc-field` 中，最近字体继承来源仍为 12px，不会因祖先容器 16px 自动变成 16px。
- **建议**：窄屏对 input/select 显式设为 16px；说明文字仍可保持较小字号。实际缩放、聚焦和 320px 下的可读性待浏览器观察，不能据静态代码宣称已通过。

### UI-REV-M02：评审状态保存了筛选，却没有恢复筛选

- **位置**：`storeState()` 保存 `filter`（190 行），初始化固定为 `all`（197 行），`apply(snapshot)` 没有采用 `snapshot.filter`（273 行）。
- **反例**：会话宿主恢复一个“已归档”筛选快照，查询和选中项恢复了，筛选却变回全部，用户看到的上下文与保存时不同。
- **建议**：初始化和 apply 时均按当前分区允许值校验恢复 filter；若不打算恢复，删除保存字段并明确该状态仅短暂保留。此问题仅限评审界面状态，不是记忆持久化或产品权限问题。

### UI-REV-M03：归档语义及旧管理动作的迁移需写清

- **位置**：DEMO-E04（165 行）只解释“不是冷记忆压缩”；经验详情动作仅“查看来源信息”（222 行）；设计稿第 8–9 节的后续组件映射没有逐项说明现有纠正/归档/恢复/删除的去向。
- **反例**：用户可能把“历史参考”理解成仍参与召回；后续按原型直接替换客户端时，也可能遗漏原本已存在的管理动作。
- **建议**：归档记录就地说明“内容保留、可恢复、不参与自动召回”；设计稿补一句已有纠正/归档/恢复/删除会放在详情局部动作，原型当前仅展示阅读子集。沿用 `client.js:173`、`176`–`178` 的删除/归档说明：明确删除不可恢复，不能包装成冷档，也不承诺撤回模型已收到内容。当前评审无需添加可执行删除按钮。

### UI-REV-M04：B 当前阅读项缺少辅助技术状态

- **位置**：A 行有 `aria-current`（239 行），B 行只用 `data-selected` 控制背景（240 行），B 记录按钮没有当前项语义。
- **反例**：屏幕阅读器可知道某行的复选框已勾选，但不知道当前右侧正在阅读哪条；勾选与打开详情是两个独立状态。
- **建议**：给当前阅读项的按钮或对应行增加适合的当前项标记，并保持复选框只表达选择。不要把两种状态合并为同一个 `aria-selected`。辅助技术实际播报仍待人工验证。

## 已核对的边界

| 核对点 | 源码观察与结论 |
|---|---|
| 来源与普通经验核验 | 普通经验只有未核验；本人保存/模型提炼是来源方式；归档详情继续显示未核验。没有虚构普通经验“已核验”按钮。年度的初审对象歧义见 I02，0.2 已关闭。 |
| 已有能力与设计候选 | 整理按钮、候选类型/文案、采用/保留动作均标出设计或演示；取消按钮 disabled，并说明 `CANCEL_UNAVAILABLE`；未知结果没有直接重发入口。证明正文审批和年度维度模板未伪装成已打通。 |
| 项目与共享权限 | 项目 picker 明确只切演示视角且复用合成记录，不证明隔离；共享示例说明 source→target 和按关系检索，不复制成当前项目事实。设计稿要求真实实施仍由可信项目绑定、现有同源管理接口和用户动作边界控制。 |
| 冷档与删除 | 没有可用冷档/再压缩/恢复按钮；原型不执行删除。初审缺少的归档说明和迁移动作映射见 M03，0.2 已补齐，不据此要求新增功能。 |
| 数据输入与 HTML | 初审为 13 条 DEMO 记录，0.2 增补 E05 后为 14 条，均为源码合成常量；正文、标题、来源、定位、选项等主要字符串经过 `escape()`，搜索值写入 input.value，不拼入 HTML。`item.id`、`item.tone` 等属性仍直接插值，只因当前是固定合成常量而可控。恢复状态对 tab/selected/decision 做允许值校验，0.2 增加 filter 按分区允许值恢复；query 不进入 HTML。 |
| 可编码迁移 | 设计稿明确未来应映射为现有 `h(...)`/React 文本节点，不能复制 `innerHTML` 模式接真实内容。迁移时 ID/tone/状态必须来自验证后的数据模型；需要动态选择器时另做安全构建，不能把真实 ID 原样拼入选择器或 HTML。整理候选不得假接旧纠正/删除操作。 |
| 外部资源与调用 | 独立静态检查未发现资源属性 src/href/action/poster/srcset、CSS @import/url()、fetch/XHR/WebSocket/EventSource/sendBeacon；离线包装有 CSP `connect-src 'none'`。存在可选 `window.openai.setWidgetState` 与本地 Tweak 接口，因此准确表述是“无原型主动网络/真实记忆 API 调用”，不是“没有任何宿主调用”。 |
| 自适应与焦点 | 有断点单列、明确返回、无固定页脚、原生输入/选择与可见焦点替代；没有把导航冒充未实现的 ARIA tabs。root 的运行覆盖 320px B 列表/A 详情和 760/1024px 两方向页面不横溢，以及两个程序打开入口的返回焦点；200% 文字缩放、完整键盘/屏幕阅读器或真实 light/dark 令牌对比度未因此获得证明。 |
| 用户选择 | 用户答复/预测仍待完成。原型内决定只属于合成候选，widgetState 不表示用户批准视觉方向、记忆写入或产品权限。 |

# 产品到软件设计：执行引导

版本1.0，2026-11-06。由根[SKILL.md](../SKILL.md)按需加载。用户最新要求为高层操作：集中确认产品方向、由设计者补足软件细节；不继续细机制问答。

## 1. 模式与交付检查

| 模式 | 首要产物 | 本轮不自动发生的事 |
|---|---|---|
| 调查收敛 | 候选比较、固定来源、关键缺口、产品建议 | 安装候选、读取凭据、扫描真实历史 |
| 产品/设计 | 产品决定记录、软件设计、实施待办、独立评审 | 按计划命令实际构建、索引、连接远端或登录 |
| 实现 | 对应设计的可运行增量、实际测试/评审/机制 | 超出本轮范围的新系统或无授权外部动作 |
| 局部变更 | 变更单、影响分析、受影响设计/用例或实现 | 整份设计推倒重写、重复确认既有选择 |

开始时写出交付清单及状态，避免把调查报告、详细设计和运行结果混为一谈。本次工作区交付清单为：根skill、05统一TODO、其余七份software-design.md及独立设计评审；不实现七项功能。

## 2. S0需求和收口

整理用户明确要求、已确认产品决定、本轮范围、允许的数据流和首版用户旅程。把每条验收写成触发/输入/动作/可观察输出/失败判据，避免只写“好用、智能、丝滑”。

对产品问题与技术决策分类：

- **问用户**：嵌入Harness还是独立应用、首版是否包含编辑器/文件回退/专用面板、是否接受明显不同的浏览器载体。
- **设计者决定并说明**：文件树、RPC字段、内部状态、阈值默认值、布局微调、分页、索引策略、去重窗口。
- **运行前补齐的外部输入**：目标站点/服务器、credentialRef、编译配置、批准Provider；它们可作为确定配置schema，不因当前没有实际值让整体设计空白。
- **必须明确的硬条件**：已知宿主缺乏所需接缝/网络隔离能力，影响承诺能否兑现时如实标门禁并设计替代，不写成已验证。

## 3. S1调查与来源锁定

先读本地调查和真实源码/安装物料，再按必要性查公开主源；外部请求不得包含本项目私有代码、日志、凭据或内网内容。记录实际查看范围与日期，动态HEAD不能作为最终部署锁。

逐来源写“版本/提交或SHA→提供的机制→采用方式→未采用部分→仍需验证的依赖/许可/运行条件”。无法取得许可或固定物料时，设计一个不依赖该候选的确定路径；不把未来下载当现成依赖。

停止条件是足够选路线并定义实现门禁，不要求搜尽所有同类产品。

## 4. S1-P高层产品确认

先形成可审阅建议，再集中提问；每个问题带短背景和目的。推荐句式：

> 【项目】你已有/目标是……。当前还需决定……，它影响首版……。建议……；另一方向是……。你希望哪种？

好的问题：浏览器原内置页若无控制接缝，是否接受明确标记的Harness内受控替代页？

不应继续问的细项：归档阈值多少天、摘要更新防抖几秒、详情面板宽度、每个按钮文字、数据库表拆分。给合理可配置默认值、理由和验证，不让用户逐条审批。

多项目可每项目一题集中呈现，必要的真正产品阻塞可补一轮；不要把用户明确过的SSH/GDB或单/多仓学习重复作为待确认。答案写入[产品决定记录](product-decisions.md)，并同步有关设计。未答的产品选择保留pending，不用预选值冒充同意；设计可先写明确分支。

## 5. S2详细设计与评审

按[设计合同](software-design-contract.md)交付。使接手编码的人无需再决定系统架构；能够按文件职责、工具签名、schema、状态和实施步骤开始工作。

每个核心旅程写一条正常时序和关键失败时序。例如发送前撤权、超时但副作用未知、同事件重放、备份恢复、source版本变化。接口使用结构化字段/错误码，不只散文描述“校验参数”。

设计者和独立评审者分开。评审关注可编码性、已核接口与本地定义接口的区分、依赖可取得性、隔离和恢复边界、公共事件一致性、是否保留局部修改能力。修订后收口为无未关闭阻断项或明确的外部运行门禁。

## 6. S3最小闭环与S4增量实现

仅在实现阶段执行：优先真实入口→真实宿主服务→本地效果→可观察证据。模型/远端可用替身，但列出替代点，不能据此称真实服务可用。

每个增量是一个可独立验收的用户行为，不机械按每个函数拆任务。对行为变化先复现失败，再最小实现；运行相应回归，源码变更或新疑点才刷新已有证据。可逆文档调整不强行新增功能测试。

## 7. S5集成、S6安装和S7机制

证据分层：组件/合同→实际安装库→隔离完整Host→实际已批准API或可信目标→出口/故障恢复。固定被审代码和运行物料，记录命令、exit、skip、unknown。只有执行过的层级可标通过。

安装前检查依赖闭包、版本与所需权限、启用/停用/卸载和回退。安装、加载、激活、用户旅程通过分别记录；已有授权不重复申请，新增超范围动作不能由设计文档推导为获准。

机制说明从实施中持续记，最终按[合同](mechanism-document-contract.md)整合。用稳定机制ID把来源、实际决策、代码、测试及skill改进假设关联起来。

## 8. 流程改进及局部修订

用户纠正流程时，先修当前做法，再同步根skill/指南/相关模板；保留变更来源。新增软件功能时按[局部修订规则](design-change-policy.md)，只改受影响部分。

不以新增文档或问答轮次衡量进度。进度输出只说明已完成什么可审阅交付、哪些产品问题仍等待、哪些运行条件尚未核验，以及下一个有限的交付。
